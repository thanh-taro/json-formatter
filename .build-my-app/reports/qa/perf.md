# Performance NFR measurements, JSON Formatter M-1

Date 2026-10-14. Build: `pnpm build` (production `dist/`), served by `E2E_PORT_BASE=4473 node tests/e2e/server.mjs` (uncompressed, so startup is a worst case; real hosting compresses to about 140 KB gzip for the main script).
Machine: Apple M3 (8 cores), 16 GB RAM, macOS 27.0.1. Load average at measurement time ranged 2 to 21 because other agents ran suites in parallel. Every row below uses the lowest-load run unless a range is given; each run records its load in the raw JSON.
Engines: Chromium 153.0.8010.12 (Playwright 1.63 headless shell, desktop viewport 1280x800), WebKit 26.6 (Playwright WebKit, system WebKit on macOS, headless). Gecko not in scope. Both are headless automation builds, not a real device or headed browser; frame times quantise to 16.7 ms.
Method: Playwright harness driving the real UI (Open file via file chooser, toolbar Minify/Beautify, Ctrl+F, tree view). Timings come from in-page `performance.now()` plus rAF polling, so they are end-to-end including file read, worker, validation and first paint. Fixtures (generated, exact byte sizes): "pretty" 1/2/5/10/50/100 MB, 2-space beautified array of records with strings (about 4 M lines at 100 MB; minify then beautify round-trips to the same size, so no RULE-02 confirm); "dense" = tests/fixtures/generated/f010-100mb (1.75 M small records on one line each; beautify grows it to 128 MB so Continue was clicked). Memory = macOS `footprint` (physical footprint incl. compressed, summed over the engine's processes); Chromium JS heap after forced GC via CDP (main + worker). `ps` RSS was rejected: it under-reports compressed pages in WebKit and over-counts shared graphics in Chromium.

## Regressions and defects found

**R1. Find match count is inflated when the term is typed (correctness, F-010; found while measuring AC6).** Opening a file whose records contain "item" 109 times and typing "item" into Find (any key delay from 30 to 400 ms) shows "1 of 218". At 1 MB it shows 7,230 for 3,615 matches, at 10 MB 72,160 for 36,080, and at 100 MB 719,126 for 359,563, in both engines, and the value stays 2x for at least 6 s. Setting the field in one go (`fill`) gives the right count; term "lorem" and "item-" typed give the right count; "ite" shows 4x (the "it" count of 3 per record plus "ite" 1), "name" 2x, which looks like the previous prefix's count being added into the new term's count. Pasting 5 records into the editor and typing "item" is correct, so the e2e checks (aaaa and the AC6 test) do not catch it; AC6 also asserts only a regex on the count, never the number. Likely cause (not root-caused): the count restart in src/editor/find.ts (`start()` builds a new FindIndex while an earlier `tick`/scan from the previous keystroke may still advance or append to the shared state). Repro: open /private/tmp/claude-501/-Users-er-lap-mam3-016-Documents-personals-taro-kit-tools-developer-tools-json-formatter/9e5bba32-da16-4a97-b3a7-1c661358ec6f/scratchpad/fx/small.json (30 KB, 109 matches), Ctrl+F, type "item" at 120 ms; script /private/tmp/claude-501/-Users-er-lap-mam3-016-Documents-personals-taro-kit-tools-developer-tools-json-formatter/9e5bba32-da16-4a97-b3a7-1c661358ec6f/scratchpad/findchk.mjs. Proposed fix: give each `start()` a generation number and have `tick`/`scanStep` callbacks drop work whose generation is stale; add an e2e assert that the final count equals the real number of matches after typing the term character by character.

**R2. First keystroke after opening Find at 100 MB paints late (NFR-02 miss, Chromium; WebKit intermittent).** Ctrl+F itself is fast (40 ms). A key typed within roughly 300 ms of opening the panel paints after 135-141 ms (6 of 6 consistent runs on two fixtures, independent of load 2-26 and of any settle time before Ctrl+F). With 300 ms or more between Ctrl+F and the first key the latency is 12-17 ms, which is also why the repo's own e2e (it waits for focus) passes. Likely cause: the first scan slice of the new search runs synchronously inside the first keystroke (`start(select, defer=false)` calls `this.tick()` at once in src/editor/find.ts) and at 100 MB the first window read/lower-case step (about 1 MB) plus panel layout costs about 120 ms. Smallest fix: when the term is first typed, schedule the first slice with the same `defer` path already used for edits (or shrink the first slice to a few hundred KB so the first match still comes within 8 ms slices).

**R3. Fast scroll can drop frames at 100 MB in Chromium (NFR-04, borderline).** Real wheel scrolling meets "no frame over 50 ms" in every run. The harder fling (3000 px per frame, similar to dragging the scrollbar) gave 0 slow frames at the quietest load, but 1-9 frames over 50 ms (max 83-100 ms) in other runs and consistently after beautify (83 ms max, 5-10 frames). Load makes it worse, so confidence is medium. Suggested follow-up: trace with the Performance panel on a headed laptop (manual item below); if it persists, reduce the editor's off-screen render margin for the very-large tier.

**R4. Transient memory above 1.5 GB in Chromium (NFR-04 wording is "after GC").** After a forced GC the footprint is 0.65-0.86 GB for the whole browser (328 MB of it JS heap), so the NFR passes as written. During a fling or beautify the renderer reaches 1.0-1.36 GB and the total 1.25-1.6 GB, and a dense 100 to 128 MB beautify reached 1.9 GB total, then falls back. The jump during scroll (about 0.9 GB on top of the settled 0.45 GB) is renderer layout/paint memory, not the JS heap. If the NFR is meant as true peak, the scroll case is the one to fix. Not a regression against D-024; no fix proposed beyond R3.
